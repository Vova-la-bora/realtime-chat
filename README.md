# Чат в реальном времени

Веб-чат: регистрация, групповые комнаты и личные диалоги, переписка в реальном времени, история с курсорной пагинацией, онлайн-статусы, «прочитано», поиск по сообщениям и реакции-эмодзи. Бэкенд работает в двух инстансах за Nginx, события между ними передаются через Redis Pub/Sub.

Реализованы все этапы ТЗ с 1 по 5 и две из трёх опциональных функций этапа 6: **поиск по сообщениям** и **реакции**. Загрузка изображений (третья опциональная функция) не реализована.

## Возможности

- **Аккаунты:** регистрация, вход, выход, обновление токена (refresh-токен в httpOnly cookie, ротация), профиль (отображаемое имя, аватар по URL).
- **Комнаты:** публичные и приватные группы, каталог публичных комнат с поиском по названию, вход, выход, приглашение владельцем, личные диалоги (для пары пользователей ровно один), список комнат с последним сообщением и счётчиком непрочитанных.
- **Сообщения:** отправка в реальном времени, оптимистичный интерфейс («отправляется» → «отправлено» / «ошибка» с повтором), идемпотентность по `clientMsgId`, история с курсорной пагинацией и бесконечной прокруткой вверх, правка («изменено») и мягкое удаление.
- **Статусы:** онлайн / «был в сети» (с учётом нескольких вкладок и инстансов), «печатает…», «прочитано» в личных диалогах, счётчики непрочитанных.
- **Поиск по сообщениям комнаты** (полнотекстовый, с учётом русской и английской морфологии) и **реакции-эмодзи** на сообщения (набор из 8 эмодзи, обновляются у всех участников сразу).
- **Масштабирование:** два инстанса бэкенда, Nginx с `least_conn`, Redis Pub/Sub между инстансами, ограничение частоты сообщений (20 за 10 секунд).
- **Интерфейс:** адаптивная вёрстка, светлая и тёмная темы, подписи для скринридеров.

## Архитектура

```
        Браузер: React + Zustand (ChatClient держит WebSocket, REST через HTTP-клиент)
                      |  REST /api                |  WebSocket /ws
                      +-------------+-------------+
                                    |
                         Nginx (web, :8080)
              раздаёт сборку фронтенда, балансирует least_conn
                       /                         \
        +------------------------+   +------------------------+
        | api1                   |   | api2                   |   одинаковые stateless-
        |  routes -> services -> |   |  routes -> services -> |   инстансы Fastify
        |       repositories     |   |       repositories     |
        |  ws: gateway ->        |   |  ws: gateway ->        |
        |      handlers ->       |   |      handlers ->       |
        |      services          |   |      services          |
        |  pubsub: roomBus       |   |  pubsub: roomBus       |
        +-----+-------------+----+   +----+-------------+-----+
              |             |             |             |
              |             +------+------+             |
              |                    |                    |
              |            Redis 7 (общий)              |
              |      Pub/Sub: room:<id>, chat:membership |
              |      presence:<userId>  rl:msg:<userId>  |
              |                                          |
              +------------- PostgreSQL 16 --------------+
                 users, rooms, room_members, messages (+ search_vector),
                 message_reactions, refresh_tokens
```

Путь сообщения:

1. Клиент шлёт `send_message` по WebSocket. Инстанс проверяет членство в комнате и лимит частоты (Redis), сохраняет сообщение в PostgreSQL (`ON CONFLICT` по `(sender_id, client_msg_id)` делает повтор безопасным) и отвечает отправителю `message_ack`.
2. Инстанс рассылает `new_message` своим подключениям комнаты и публикует событие в канал Redis `room:<id>`.
3. Второй инстанс получает событие из Redis и доставляет его своим подключениям; собственные сообщения шины инстанс отбрасывает по имени источника.

Правка, удаление, реакции, «печатает…», «прочитано» и статусы присутствия идут тем же путём (шаги 2–3); подробности и проверки: разделы «Масштабирование» и «Нагрузка и производительность».

## Стек

Бэкенд: Node.js 20 + TypeScript, Fastify, `ws` (чистый WebSocket), PostgreSQL 16, Redis 7 (онлайн-статусы, `ioredis`),
Zod, argon2, JWT, node-pg-migrate. Фронтенд: React 18 + TypeScript + Vite, React Router, Zustand, CSS Modules.
Тесты: Vitest (83 теста бэкенда, 55 тестов фронтенда). Запуск: Docker Compose, Nginx. Нагрузка: k6.

## Быстрый старт

```bash
cp .env.example .env
docker compose up --build
```

- Приложение: **http://localhost:8080** (Nginx раздаёт фронтенд и балансирует `/api` и `/ws` между двумя инстансами бэкенда).
- Инстансы напрямую: `api1` на `http://localhost:3000`, `api2` на `http://localhost:3001`. Проверка: `curl http://localhost:8080/health` несколько раз подряд покажет, какой инстанс ответил (`"instance": "api1"` или `"api2"`).

Миграции применяются автоматически при старте контейнера `api`.

Сценарий для проверки в браузере: регистрация, создание комнаты, переписка, прокрутка вверх (подгрузка истории).

найдите комнату в каталоге и войдите в неё.

## Проверка API через curl

Нужны `curl` и `jq` (Git Bash, WSL или Linux/macOS).

```bash
# 1. Регистрация двух пользователей (refresh-токен сохраняется в cookies.txt)
ALICE=$(curl -s -c cookies.txt -X POST localhost:3000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"alice","email":"alice@example.com","password":"password123"}')
echo "$ALICE" | jq .
ALICE_TOKEN=$(echo "$ALICE" | jq -r .accessToken)
ALICE_ID=$(echo "$ALICE" | jq -r .user.id)

BOB=$(curl -s -X POST localhost:3000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"bob","email":"bob@example.com","password":"password123"}')
BOB_TOKEN=$(echo "$BOB" | jq -r .accessToken)
BOB_ID=$(echo "$BOB" | jq -r .user.id)

# 2. Вход и обновление токена по refresh-cookie
curl -s -X POST localhost:3000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"alice@example.com","password":"password123"}' | jq .
curl -s -b cookies.txt -c cookies.txt -X POST localhost:3000/api/auth/refresh | jq .

# 3. Профиль
curl -s localhost:3000/api/users/me -H "Authorization: Bearer $ALICE_TOKEN" | jq .
curl -s -X PATCH localhost:3000/api/users/me -H "Authorization: Bearer $ALICE_TOKEN" \
  -H 'Content-Type: application/json' -d '{"displayName":"Алиса"}' | jq .
curl -s "localhost:3000/api/users?query=bo" -H "Authorization: Bearer $ALICE_TOKEN" | jq .

# 4. Комнаты: создание, каталог, вход, приглашение, личный диалог
ROOM_ID=$(curl -s -X POST localhost:3000/api/rooms -H "Authorization: Bearer $ALICE_TOKEN" \
  -H 'Content-Type: application/json' -d '{"name":"general","type":"public"}' | jq -r .room.id)
curl -s "localhost:3000/api/rooms/public?query=gen" -H "Authorization: Bearer $BOB_TOKEN" | jq .
curl -s -X POST localhost:3000/api/rooms/$ROOM_ID/join -H "Authorization: Bearer $BOB_TOKEN" | jq .
curl -s -X POST localhost:3000/api/rooms/direct -H "Authorization: Bearer $ALICE_TOKEN" \
  -H 'Content-Type: application/json' -d "{\"userId\":$BOB_ID}" | jq .
curl -s localhost:3000/api/rooms -H "Authorization: Bearer $BOB_TOKEN" | jq .
curl -s localhost:3000/api/rooms/$ROOM_ID/members -H "Authorization: Bearer $BOB_TOKEN" | jq .

# 5. История с курсорной пагинацией. Сообщения отправляются по WebSocket (см. ниже),
#    а чтобы быстро получить длинную историю, добавим 120 тестовых сообщений скриптом:
docker compose exec api node scripts/seed-messages.js $ROOM_ID $ALICE_ID 120
curl -s "localhost:3000/api/rooms/$ROOM_ID/messages" -H "Authorization: Bearer $BOB_TOKEN" | jq '{hasMore, nextCursor, first: .items[0].id, last: .items[-1].id}'
# следующая страница: before_id = nextCursor из предыдущего ответа
curl -s "localhost:3000/api/rooms/$ROOM_ID/messages?before_id=71&limit=50" -H "Authorization: Bearer $BOB_TOKEN" | jq '{hasMore, nextCursor}'

# 6. Поиск по сообщениям комнаты (только для участников): query от 2 до 100 символов, limit 1–50 (по умолчанию 20),
#    курсор before_id работает так же, как в истории. Ниже запрос «тестовое»: в Git Bash на Windows кириллицу
#    в аргументах curl нужно кодировать вручную, иначе она искажается.
curl -s "localhost:3000/api/rooms/$ROOM_ID/search?query=%D1%82%D0%B5%D1%81%D1%82%D0%BE%D0%B2%D0%BE%D0%B5&limit=2" \
  -H "Authorization: Bearer $BOB_TOKEN" | jq '{hasMore, nextCursor, found: [.items[].content]}'
curl -s "localhost:3000/api/rooms/$ROOM_ID/search?query=%D1%82%D0%B5%D1%81%D1%82%D0%BE%D0%B2%D0%BE%D0%B5&limit=2&before_id=119" \
  -H "Authorization: Bearer $BOB_TOKEN" | jq '{hasMore, nextCursor}'
```

Синтаксис запроса поиска как у веб-поисковиков: несколько слов — все сразу, `"точная фраза"`, `-исключить`, `слово1 or слово2`. Каждое сообщение в истории и в результатах поиска содержит поле `reactions`: `[{ "emoji": "👍", "count": 2, "userIds": [1, 5] }]`. Реакции ставятся по WebSocket (событие `toggle_reaction`, см. ниже).

Формат ошибок: `{ "error": { "code": "...", "message": "..." } }`.

## WebSocket

Подключение: `ws://localhost:3000/ws?token=<accessToken>`. Токен проверяется при рукопожатии,
невалидный или отсутствующий токен: соединение закрывается с кодом **4401**.
Все кадры имеют вид `{ "type": "...", "payload": {...} }`, максимальный размер кадра 16 КБ
(больше: закрытие с кодом 1009).

События:

| Направление | type | payload |
|---|---|---|
| клиент → сервер | `join_room` | `{ roomId }` подписаться на события комнаты (только участнику) |
| клиент → сервер | `leave_room` | `{ roomId }` отписаться (членство в комнате не меняется) |
| клиент → сервер | `send_message` | `{ roomId, content, clientMsgId }`, `content` 1–4000 символов, `clientMsgId` UUID |
| клиент → сервер | `edit_message` | `{ messageId, content }` изменить своё сообщение |
| клиент → сервер | `delete_message` | `{ messageId }` удалить своё сообщение (мягко) |
| клиент → сервер | `typing` | `{ roomId }` «печатает…» |
| клиент → сервер | `mark_read` | `{ roomId, messageId }` комната прочитана до этого сообщения |
| клиент → сервер | `toggle_reaction` | `{ messageId, emoji }` поставить реакцию, а если она уже стоит, снять; `emoji` из набора `👍 👎 ❤️ 😂 😮 😢 🎉 🔥` |
| клиент → сервер | `ping` | `{}` |
| сервер → клиент | `message_ack` | `{ clientMsgId, message }` подтверждение отправителю |
| сервер → клиент | `new_message` | `{ message }` остальным подключениям комнаты |
| сервер → клиент | `message_edited` | `{ message }` всем подключениям комнаты, включая автора |
| сервер → клиент | `message_deleted` | `{ roomId, messageId }` всем подключениям комнаты |
| сервер → клиент | `user_typing` | `{ roomId, userId }` всем, кроме подключений самого печатающего |
| сервер → клиент | `presence_update` | `{ userId, online, lastSeenAt }` тем, кто слушает общие с пользователем комнаты |
| сервер → клиент | `message_read` | `{ roomId, userId, messageId }` всем подключениям комнаты, кроме отправившего отметку |
| сервер → клиент | `reaction_updated` | `{ roomId, messageId, reactions }` всем подключениям комнаты, включая поставившего; `reactions` — полный актуальный набор сообщения |
| сервер → клиент | `error` | `{ code, message, refTo? }`, `refTo` = `clientMsgId`, если он был в запросе |
| сервер → клиент | `pong` | `{}` |

Как это работает:

- Чтобы получать `new_message`, подключение должно выполнить `join_room` для комнаты. Отправлять сообщения можно и без подписки, если вы участник комнаты.
- Права проверяются на каждое событие. Не участник получает `error` с кодом `not_a_member`; сообщение не сохраняется.
- Повторная отправка с тем же `clientMsgId` не создаёт дубль: сервер повторно отвечает `message_ack` с уже сохранённым сообщением и не рассылает его второй раз.
- Отправитель получает `message_ack`, а не `new_message`. Остальные его вкладки получают `new_message`.
- Кадры одного подключения обрабатываются строго по порядку, поэтому после `join_room` можно сразу слать `send_message`.
- Heartbeat: клиент шлёт `ping` каждые 25 секунд; подключение без активности дольше 60 секунд закрывается (код 4408).
- Rate limiting: не более 20 сообщений за 10 секунд на пользователя (общий счётчик в Redis для всех вкладок и инстансов). Превышение отвечает `error` с кодом `rate_limited` и `refTo` = `clientMsgId`, сообщение не сохраняется; на остальные события (`typing`, `mark_read`, правку) лимит не распространяется.
- События доходят до подписчиков комнаты на любом инстансе: см. раздел «Масштабирование».
- Если пользователь выходит из комнаты через REST, его подключения отписываются от неё автоматически. И наоборот: после вступления, приглашения или создания личного диалога все подключения пользователя подписываются на комнату сами, без `join_room`.
- Новые события проверяют права так же, как `send_message`: править и удалять можно только свои сообщения (иначе `forbidden`), все события требуют членства в комнате (иначе `not_a_member`), `mark_read` отвергает сообщение не из этой комнаты (`invalid_message`).
- `toggle_reaction`: реакция ставится на любое чужое или своё сообщение комнаты, где вы участник (`not_a_member` иначе, `message_not_found` для несуществующего сообщения, `message_deleted` для удалённого, `validation_error` для эмодзи вне набора). Один пользователь может поставить на сообщение несколько разных эмодзи, но каждое только один раз.

Быстрая проверка из консоли (нужен `npx`, два терминала с разными токенами):

```bash
npx wscat -c "ws://localhost:3000/ws?token=$ALICE_TOKEN"
> {"type":"join_room","payload":{"roomId":1}}
> {"type":"send_message","payload":{"roomId":1,"content":"Привет","clientMsgId":"3f0c1d4e-8a52-4c3a-9b27-5e2f6a1d7c90"}}
```

## Принятые решения (этап 1)

- **Миграции: node-pg-migrate.** Лёгкий инструмент без ORM, миграции пишутся в терминах SQL, как и весь доступ к данным в проекте. Prisma избыточна для набора из пяти таблиц и сложных запросов с `LATERAL`.
- **Хеширование паролей: argon2.**
- **Вход по email и паролю** (`POST /api/auth/login { email, password }`).
- **`refresh` и `logout` аутентифицируются refresh-cookie, а не заголовком Bearer**: к моменту обновления access-токен уже просрочен.
- **Refresh-токены ротируются:** при каждом обновлении старый отзывается, в БД хранится только SHA-256 хеш.
- **Приглашение (`/invite`) сразу добавляет пользователя в участники,** отдельной сущности «приглашение» в ТЗ нет.
- **Если владелец покидает группу,** роль `owner` получает самый давний участник.
- **Онлайн-статусы** в `/members` на этапе 1 были заглушкой (`false`), с этапа 4 они берутся из Redis.
- **Сервис `web`** появился на этапе 3 вместе с фронтендом. **Redis** используется с этапа 4 (онлайн-статусы), а с этапа 5 ещё и для Pub/Sub между инстансами и rate limiting.
- **Размер страниц:** история по умолчанию 50 сообщений (максимум 100), каталог публичных комнат 20.

### Решения этапа 2

- **`ws` без обёрток:** сервер `WebSocketServer` работает в режиме `noServer` на том же HTTP-сервере Fastify (путь `/ws`), поэтому HTTP и WebSocket делят один порт. Закрытие с кодом 4401 возможно только после рукопожатия, потому токен проверяется сразу после апгрейда.
- **Подписка явная:** сервер не подписывает подключение на все комнаты пользователя автоматически, клиент сам вызывает `join_room` для нужных комнат (фронтенд делает это для всех комнат из списка).
- **Подписки хранятся в памяти инстанса** (`ws/roomSubscriptions.ts`), а доставку между инстансами с этапа 5 обеспечивает Redis Pub/Sub (см. «Масштабирование»).
- **Идемпотентность на уровне БД:** `INSERT ... ON CONFLICT (sender_id, client_msg_id) DO NOTHING`, затем чтение уже сохранённой записи. Дубль не создаётся даже при одновременных повторах.
- **Порядок обработки:** кадры одного подключения идут через очередь, чтобы `join_room` и следующий за ним `send_message` не обгоняли друг друга.
- **Прочие события из ТЗ** (`edit_message`, `delete_message`, `typing`, `mark_read`) на этапе 2 отвечали ошибкой `unknown_type`; полностью они заработали на этапе 4.

### Решения этапа 3

- **Один origin.** Nginx отдаёт и страницу, и API, и WebSocket, поэтому refresh-cookie (`SameSite=Strict`, путь `/api/auth`) работает без настройки CORS. В разработке то же делает прокси Vite.
- **Access-токен хранится только в памяти** (не в `localStorage`), чтобы XSS не мог его украсть. После перезагрузки страницы сессия восстанавливается по httpOnly refresh-cookie.
- **Автообновление токена:** при ответе 401 HTTP-клиент один раз обновляет токен (параллельные запросы делят один refresh) и повторяет запрос. Если WebSocket закрыт кодом 4401, клиент так же обновляет токен и переподключается.
- **Переподключение:** задержка 1с, 2с, 4с ... максимум 30 с, с джиттером (50–100% от базы); сбрасывается при успешном подключении; при возврате сети (`online`) подключение выполняется сразу. Heartbeat: `ping` каждые 25 секунд.
- **Пропущенные сообщения после обрыва.** В REST нет параметра «после id», поэтому клиент листает историю от новых к старым, пока не дойдёт до последнего известного id (не больше 10 страниц), и сливает результат с уже загруженным. Если разрыв слишком большой, остаются только свежие сообщения, а старые догружаются прокруткой.
- **Оптимистичная отправка:** сообщение сразу появляется со статусом «отправляется», после `message_ack` становится «отправлено». Если соединения нет, оно потеряно или сервер не ответил за 10 секунд, показывается «ошибка» и кнопка «Повторить». Повтор использует тот же `clientMsgId`, поэтому дубля не будет.
- **Бесконечная прокрутка вверх:** при приближении к верху загружается следующая страница (курсор `nextCursor`), положение прокрутки сохраняется. Если сообщений мало и прокрутки нет, история догружается сама.
- **Подписка на комнаты:** после подключения клиент делает `join_room` для каждой комнаты из списка, а также для новой после создания или входа.
- **Безопасность вывода:** текст сообщений выводится как обычный текст React, `dangerouslySetInnerHTML` нигде не используется.
- **Интерфейс:** адаптивная вёрстка (на узких экранах список комнат и чат показываются по очереди), светлая и тёмная темы (системная по умолчанию, переключатель запоминается), подписи для скринридеров и видимый фокус.

### Решения этапа 4

- **Онлайн-статус в Redis.** Для каждого пользователя хранится множество `presence:<userId>`: `connId` → время истечения (мс, +90 с). Heartbeat продлевает срок (не чаще раза в 20 с), просроченные записи вычищаются при каждом обращении, так что обрыв без `close` не оставляет пользователя «онлайн» дольше срока жизни записи. Пользователь онлайн, пока в множестве есть хотя бы одна живая запись, то есть пока открыта хотя бы одна вкладка или устройство.
- **`last_seen_at`** записывается в БД, когда закрывается последнее подключение, и сразу рассылается вместе с `presence_update { online: false }`. Первое подключение рассылает `online: true`.
- **Кому уходит `presence_update`:** подключениям, подписанным на любую комнату, общую с пользователем (комнаты берутся из БД).
- **`mark_read` двигает отметку только вперёд** (`last_read_message_id` никогда не уменьшается) и проверяет, что сообщение существует в этой комнате. Если отметка не сдвинулась, ничего не рассылается. Своя же отметка с другой вкладки приходит как `message_read`, поэтому счётчик сбрасывается на всех вкладках пользователя.
- **Счётчик непрочитанных** считается на сервере по `last_read_message_id`: чужие неудалённые сообщения с `id` больше отметки. Клиент отправляет `mark_read`, когда комната открыта, вкладка видна и загружены сообщения (при открытии, при новом входящем, при возврате на вкладку, после переподключения).
- **«Прочитано» только в личных диалогах:** сообщение помечено ✓✓, если его `id` не больше отметки собеседника (она приходит в списке участников и событием `message_read`). В группах виден только счётчик.
- **«Печатает…».** Клиент шлёт `typing` не чаще раза в 2 секунды; индикатор гаснет через 3 секунды без событий или при сообщении от этого пользователя.
- **Правка и удаление.** Правка обновляет `content` и `edited_at`, удаление ставит `deleted_at` (текст остаётся в БД, клиентам отдаётся «сообщение удалено»). Результат приходит событиями `message_edited` и `message_deleted` всем подключениям комнаты, включая вкладку автора, отдельного `ack` для них нет. Повторное удаление ничего не рассылает.
- **Участники комнаты** (`GET /api/rooms/:id/members`) теперь содержат `online`, `lastSeenAt` и `lastReadMessageId`.
- **Тесты бэкенда используют `ioredis-mock`** (подключение к Redis внедряется в `buildApp({ redis })`), чтобы не требовать Redis для `npm test`. В Docker приложение работает с настоящим Redis.

### Решения этапа 5

- **Два явных сервиса `api1` и `api2` вместо `--scale`:** у них постоянные DNS-имена, на которые ссылается `upstream` в Nginx (Nginx разрешает имена при старте и не отслеживает смену адресов реплик), и у каждого своё имя инстанса для Pub/Sub. Образ собирается один (`realtime-chat-api:local`).
- **Локальная доставка идёт напрямую, а не через Redis:** событие сразу уходит подключениям своего инстанса и параллельно публикуется остальным. Задержка локальным получателям не зависит от Redis, а свои собственные Pub/Sub-сообщения инстанс отбрасывает по имени источника.
- **Rate limiting на скользящем окне, а не на фиксированном:** фиксированное окно пропускает до 40 сообщений на стыке двух интервалов, что нарушает «не более 20 за 10 секунд». Отклонённые попытки в квоту не засчитываются. При недоступном Redis ограничитель пропускает сообщения (отказоустойчивость важнее строгого лимита).
- **`least_conn` в Nginx:** подключения WebSocket долгие, поэтому новые направляются на инстанс с меньшим числом активных соединений.
- **Для двух инстансов в одном процессе в тестах** используются отдельные подключения `ioredis-mock` с общими данными и Pub/Sub (`createTestApp({ instanceId, ownRedis: true })`).

### Решения этапа 6

- **Поиск средствами PostgreSQL, без отдельного поискового движка.** В таблице `messages` появился сгенерированный столбец `search_vector = to_tsvector('russian', content)` (`GENERATED ALWAYS AS ... STORED`): он обновляется сам при вставке и правке, поэтому отредактированное сообщение ищется по новому тексту. Индекс GIN построен по `(room_id, search_vector)`: расширение `btree_gin` позволяет положить `room_id` в тот же GIN-индекс, и запрос фильтруется по комнате прямо в индексе. Миграция `1700000000001_search_and_reactions.js`.
- **Запрос через `websearch_to_tsquery`.** Он понимает слова, `"фразу в кавычках"`, `-исключение` и `or`, а неправильный ввод (скобки, кавычки, SQL) не вызывает ошибку, а воспринимается как обычный текст. Конфигурация `russian` приводит слова к основе: «архитектура» находит «архитектуру», «running» находит «runs».
- **Выдача устроена как история:** от новых к старым, курсор `before_id`, 20 результатов на страницу (максимум 50), ответ `{ items, hasMore, nextCursor }`. Удалённые сообщения не ищутся, искать можно только в комнатах, где вы участник, запрос не короче 2 символов.
- **Реакции хранятся в отдельной таблице** `message_reactions` с первичным ключом `(message_id, user_id, emoji)`, поэтому дубль одной реакции невозможен на уровне БД, а при удалении сообщения или пользователя строки удаляются каскадом.
- **Переключение одним SQL-запросом** (`DELETE ... RETURNING` и `INSERT ... WHERE NOT EXISTS` в одном CTE): запрос не зависит от предыдущего чтения, а два одновременных нажатия никогда не оставят дубль.
- **Сервер шлёт полный набор реакций сообщения, а не «+1» / «−1».** Событие `reaction_updated` не зависит от предыдущих: пропущенное событие исправляется следующим, и клиенту не нужно вести счётчики. Рассылка идёт всем подключениям комнаты, включая нажавшего, через ту же шину между инстансами, что и остальные события.
- **Набор эмодзи фиксирован** (8 штук): сервер проверяет его Zod-схемой события и не принимает произвольные строки, а клиент показывает тот же список.
- **Интерфейс.** Кнопка «Поиск» в шапке чата открывает панель: запрос уходит на сервер через 300 мс после последнего нажатия клавиши, устаревшие ответы отбрасываются, найденные слова подсвечиваются, следующие страницы подгружаются кнопкой «Показать ещё». Реакции показаны чипами под сообщением (своя реакция выделена рамкой, при наведении видны имена), кнопка «Реакция» открывает выбор эмодзи, повторное нажатие на чип снимает реакцию.
- **`SELECT *` в запросах к сообщениям заменён списком столбцов:** у таблицы теперь служебный столбец `search_vector`, который не нужно возвращать с каждым сообщением.
- **Разбор массивов `bigint` в `db.ts`.** Драйвер `pg` отдаёт `bigint[]` строками, а в реакциях это идентификаторы пользователей; парсер настроен так же, как для одиночного `bigint`.
- **Проверка при разработке.** Тесты нашли ошибку в первой версии: `userIds` приходили строками. Исправлено вместе с тестами на формат (`backend/test/reactions.test.ts`, `search.test.ts`).
- **Миграции при старте двух инстансов.** Контейнер повторяет `npm run migrate:up`, пока соседний инстанс держит блокировку, а не падает и перезапускается по политике `restart` (так было, пока при проверке на пустой БД один из инстансов не завершился с ошибкой «Another migration is already running»).

## Масштабирование

Бэкенд не хранит состояния между запросами, поэтому его запускают в нескольких экземплярах. В `docker-compose.yml` их два (`api1`, `api2`), общие БД и Redis, перед ними Nginx.

```
                      браузер
                         |
                  Nginx (web :8080)
          раздаёт фронтенд, /api и /ws -> least_conn
               /                       \
        api1 (Fastify + ws)        api2 (Fastify + ws)
        подключения клиентов       подключения клиентов
               \        Pub/Sub         /
                \  room:<id>, chat:membership
                 +------- Redis -------+      онлайн-статусы (presence:<id>)
                 |                     |      rate limiting (rl:msg:<id>)
                 +------ PostgreSQL ---+      сообщения, комнаты, last_read
```

Как это устроено:

- **Доставка между инстансами.** Событие комнаты (`new_message`, `message_edited`, `message_deleted`, `user_typing`, `message_read`, `presence_update`) сначала доставляется локальным подключениям инстанса, затем публикуется в канал Redis `room:<id>` с именем инстанса-источника. Остальные инстансы доставляют его своим подключениям, а свои собственные сообщения пропускают, поэтому дублей нет. `message_ack` уходит только отправителю на его инстансе.
- **Подписка на каналы по требованию.** Инстанс подписывается на `room:<id>`, когда в комнате появляется первое его подключение, и отписывается, когда уходит последнее (`pubsub/roomBus.ts`, `ws/roomSubscriptions.ts`). После `join_room` сервер дожидается оформления подписки, чтобы не потерять события, опубликованные другим инстансом в этот момент.
- **Изменения состава комнаты** (вход, выход, приглашение, создание диалога) через REST на одном инстансе публикуются в канал `chat:membership`, и остальные инстансы подписывают или отписывают подключения этого пользователя у себя. Поэтому вышедший из комнаты пользователь не получает её события, даже если его WebSocket держит другой инстанс.
- **Онлайн-статус** общий (Redis, см. решения этапа 4): пользователь офлайн, только когда закрылось его последнее подключение на любом инстансе. Событие `presence_update` отправляется в каналы всех общих комнат, а подключение, сидящее в нескольких из них, получает его один раз.
- **Rate limiting** считается в Redis на скользящем окне (`services/rateLimiter.ts`), поэтому лимит один на пользователя независимо от вкладки и инстанса. При недоступности Redis отправка не блокируется (лимит отключается, в лог пишется предупреждение).
- **Балансировка.** Nginx направляет новое подключение на инстанс с наименьшим числом активных соединений (`least_conn`); WebSocket остаётся на выбранном инстансе, пока открыт, `proxy_read_timeout` 75 с. REST без состояния, ему всё равно, на какой инстанс попасть. Токены и refresh-cookie действуют на любом инстансе.
- **Миграции** при одновременном старте обоих инстансов применяет первый, второй ждёт блокировку `node-pg-migrate` и повторяет попытку каждые 2 секунды (цикл в `CMD` образа бэкенда), после чего видит, что применять нечего.

Проверка вручную после `docker compose up --build`:

```bash
for i in 1 2 3 4; do curl -s localhost:8080/health; echo; done   # ответы api1 и api2 чередуются
docker compose stop api2                                          # приложение продолжает работать на api1 (проверено)
docker compose start api2
```

Для проверки доставки между инстансами откройте чат в двух окнах: Nginx разнесёт подключения по инстансам, а `docker compose logs api1 api2` покажет, какой инстанс принял какое подключение. Автоматически это проверяют тесты `backend/test/scaling.test.ts` (два инстанса в одном процессе, каждый со своим подключением к Redis).

## Нагрузка и производительность

### История на таблице в 1 млн сообщений

Скрипт `backend/scripts/explain-history.js` создаёт 1 000 000 сообщений в 100 комнатах (по 10 000 в комнате), делает `VACUUM ANALYZE` и печатает `EXPLAIN (ANALYZE, BUFFERS)` для запроса страницы истории (запрашивается 51 строка, чтобы определить `hasMore`):

```bash
cd backend
DATABASE_URL=postgres://chat:chat_dev_password@localhost:5432/chat_test node scripts/explain-history.js 1000000 100
```

Результат (PostgreSQL 16.15 из Docker-образа `postgres:16-alpine`, 1 000 000 сообщений, 9 запусков каждого запроса):

| Запрос | План | Время выполнения (мин / медиана / макс) |
|---|---|---|
| первая страница (`ORDER BY id DESC LIMIT 51`) | Index Scan по `messages_room_id_id_desc_idx`, 54 буфера, без сортировки | 0,096 / 0,142 / 0,191 мс |
| страница из середины (`id < $cursor`) | Index Scan по тому же индексу, 55 буферов | 0,097 / 0,110 / 0,137 мс |

Требование «не более 50 мс» выполнено с запасом в сотни раз: курсорная пагинация читает ровно одну страницу индекса независимо от глубины. Тот же замер на PostgreSQL 18.6 дал тот же план и время порядка 0,1 мс.

После этапа 6 к странице истории добавился один запрос реакций (`WHERE message_id = ANY(...)` по первичному ключу таблицы `message_reactions`); отдельно он не замерялся: на странице из 50 сообщений это 50 поисков по индексу.

### Поиск на таблице в 1 млн сообщений

Скрипт `backend/scripts/explain-search.js` создаёт 1 000 000 сообщений в 100 комнатах (по 10 000), делает `VACUUM ANALYZE` и печатает `EXPLAIN (ANALYZE, BUFFERS)` для запросов, которые выполняет `MessageRepository.search` (запрашивается 21 строка). Миграции в базе должны быть применены:

```bash
cd backend
DATABASE_URL=postgres://chat:chat_dev_password@localhost:5432/chat_test node scripts/explain-search.js 1000000 100
```

Результат (PostgreSQL 16.15 из Docker-образа `postgres:16-alpine`, 9 запусков каждого запроса). Таблица занимает 205 МБ, индекс поиска `(room_id, search_vector)` 75 МБ; вставка миллиона строк вместе с построением индекса заняла 97 секунд.

| Запрос | План | Время выполнения (мин / медиана / макс) |
|---|---|---|
| слово «релиз», 1000 совпадений в комнате, первая страница | Index Scan по `messages_room_id_id_desc_idx` с фильтром по `search_vector`: берёт самые новые сообщения комнаты, пока не наберёт 21 совпадение (просмотрено ~200 строк), 204 буфера | 0,295 / 0,393 / 0,504 мс |
| то же слово, страница из середины (`id < $cursor`) | тот же план, 215 буферов | 0,317 / 0,343 / 1,459 мс |
| два слова «релиз проекта», 100 совпадений | Bitmap Index Scan по GIN-индексу `messages_room_search_idx`, затем сортировка top-N, 171 буфер | 2,827 / 3,381 / 4,036 мс |
| слова нет в сообщениях | Bitmap Index Scan по GIN-индексу, 9 буферов | 0,18 / 0,200 / 0,253 мс |

Планировщик сам выбирает способ: для частых слов быстрее идти по индексу комнаты от новых сообщений к старым, для редких слов и сочетаний слов GIN-индекс отбирает совпадения напрямую. Оговорки: данные синтетические (словарь из десяти слов, поэтому каждое слово встречается в 10% сообщений), замер на одном соединении без параллельной нагрузки, а худший случай (слово средней частоты в комнате с миллионами сообщений) отдельно не мерился.

### Задержка доставки при 1000 соединениях (k6)

Сценарий `loadtest/ws-load.js` (k6) и подготовка данных `loadtest/seed.mjs`. Запуск после `docker compose up -d --build`:

```bash
node loadtest/seed.mjs http://localhost:8080 1000 10          # 1000 пользователей, комнаты по 10 человек
docker compose --profile loadtest run --rm k6 run --summary-export=/loadtest/summary.json /loadtest/ws-load.js
```

Каждый пользователь держит WebSocket, подписывается на свою комнату и раз в ~5 секунд пишет; время отправки зашито в текст сообщения, получатель считает разницу с текущим временем (все клиенты работают в одном процессе k6, часы общие). Подключения запускаются равномерно за 30 секунд, затем 60 секунд нагрузки. Пороги теста взяты из ТЗ: p95 доставки и подтверждения меньше 200 мс. Токены живут 15 минут, поэтому `seed.mjs` нужно запускать прямо перед тестом.

Результат прогона (k6 v2.3.0 в контейнере, трафик идёт через Nginx на `api1` и `api2`, настоящие Redis 7 и PostgreSQL 16, всё в Docker Desktop с 2 процессорами и 3 ГБ памяти):

| Метрика | Значение |
|---|---|
| Одновременные WebSocket-соединения | 1000 (все 1000 подключились, ответ 101) |
| Отправлено сообщений | 13 730 (~152 сообщения/с) |
| Доставлено получателям | 123 354 (~1366 доставок/с) |
| Задержка доставки: среднее / медиана / p90 / **p95** / макс | 11,6 / 7 / 17 / **33** / 261 мс |
| Задержка подтверждения отправителю: среднее / медиана / p90 / **p95** / макс | 11,2 / 7 / 17 / **31** / 258 мс |
| Установка соединения (`ws_connecting`): среднее / p95 | 3 / 6,9 мс |
| Пороги | p95 доставки < 200 мс: выполнен (33 мс); p95 подтверждения < 200 мс: выполнен (31 мс); проверки: 100% |

Требование ТЗ «доставка в пределах 200 мс при 1000 соединениях» выполнено с большим запасом. Доставлено 99,83% от ожидаемого числа (13 730 сообщений × 9 получателей = 123 570): расхождение в 216 копий (24 сообщения) приходится на конец теста, когда все сокеты закрываются одновременно, и сообщения, отправленные за последние миллисекунды, не успевают дойти. Отдельно потери Pub/Sub при этом не изучались.

Что нужно знать об измерении: Docker Desktop выделял системе всего 2 процессора и 3 ГБ памяти на всё сразу (k6, два инстанса, Nginx, PostgreSQL, Redis), поэтому на обычном сервере запас будет больше. В тесте нет редактирования, «печатает…» и «прочитано», только отправка и доставка сообщений; запись в БД (`INSERT` на каждое сообщение) и рассылка между инстансами через Redis в нём присутствуют.

### Проверка двух инстансов вручную (Docker)

Помимо автотестов (где оба инстанса работают в одном процессе), поведение проверено на двух отдельных контейнерах с настоящим Redis скриптом `loadtest/cross-instance-check.mjs` (`node loadtest/cross-instance-check.mjs`, адреса инстансов задаются `API1_URL` и `API2_URL`), который подключает клиентов напрямую к `api1` и `api2`: все 16 проверок прошли. Они покрывают токен, выданный одним инстансом и принятый другим; доставку `new_message`, `message_edited`, `message_deleted`, `user_typing`, `message_read`, `presence_update` между инстансами (задержка ~8–10 мс); отсутствие дублей при повторе `clientMsgId` через другой инстанс; отписку при выходе через REST на другом инстансе; автоподписку приглашённого; онлайн-статус при подключениях на обоих инстансах и общий лимит сообщений (при 30 попытках через два инстанса принято 15, отклонено 15 с учётом уже отправленных в окне).

Отдельно проверено:

- при одновременном старте двух инстансов на пустой БД схему применил `api1`, `api2` дождался блокировки миграций, повторил попытку, ничего не применил и запустился без перезапуска контейнера (`RestartCount` 0);
- `/health` через Nginx чередует `api1` и `api2` (4 и 4 из 8 запросов);
- при остановленном `api2` все запросы успешны и уходят на `api1`; после `docker compose start api2` трафик возвращается к обоим. Для этого в `nginx.conf` задан `proxy_connect_timeout 3s`: без него Nginx ждал бы подключения к остановленному контейнеру до минуты.

## Известные ограничения

- Pub/Sub в Redis не гарантирует доставку: событие, опубликованное в момент обрыва связи инстанса с Redis, теряется. Пропущенное сообщение клиент увидит после следующего переподключения WebSocket (он докачивает историю через REST) или перезагрузки страницы. Подписчик, который подключился к каналу позже публикации, прошлых событий не получает: события статусов, опубликованные до подписки, клиент восстанавливает списком участников.
- Если процесс бэкенда упадёт без штатного завершения, `presence_update { online: false }` и `last_seen_at` для его пользователей не запишутся: записи в Redis просто истекут, а запросы статуса уже будут считать их офлайн.
- Статусы присутствия берутся только из подключений WebSocket: открытая страница без соединения (например, во время переподключения) считается офлайн.
- При удалении сообщения в комнате, которая сейчас не открыта, клиент обновляет список комнат запросом, а не пересчитывает счётчик локально.
- Если в комнату приглашают, пока пользователь в сети, WebSocket-подключение подписывается на неё сразу, а в списке комната появится с первым сообщением (клиент сам перезагрузит список) или после обновления страницы: отдельного события «вас добавили» в протоколе ТЗ нет.
- Access-токен проверяется только при подключении: уже открытое WebSocket-соединение продолжает работать после истечения срока токена (клиент переподключается с новым токеном).
- Загрузка изображений (опциональный этап 6 ТЗ) не реализована.
- Поиск ищет только по тексту сообщений и только в одной комнате: искать сразу по всем комнатам нельзя. Найденное сообщение показывается в панели поиска, перехода к его месту в истории нет (в REST нет «окна вокруг id»). Результаты — снимок на момент запроса: правка и удаление сообщения в уже показанном списке не отражаются, пока запрос не повторят.
- Подсветка найденных слов делается на клиенте по простому правилу (слово запроса без окончания сравнивается с началом слов текста), а не по ответу сервера, поэтому иногда подсвечивается лишнее или пропускаются формы слова с другой основой; сами результаты определяет только сервер.
- Реакции: набор из 8 эмодзи фиксирован, события `toggle_reaction` не ограничиваются по частоте (лимит 20 в 10 секунд действует только на сообщения), реакции не меняют счётчики непрочитанных и «последнее сообщение» в списке комнат, в панели поиска реакции не показываются (в ответе API они есть).
